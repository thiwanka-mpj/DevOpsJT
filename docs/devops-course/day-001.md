# Day 001 - What is DevOps? Why DevOps? How to Introduce Yourself in a DevOps Interview



## What we cover in this lesson?

There are **04 classic DevOps-interview questions** that every beginner must be able to answer confidently.

1. What is DevOps?
2. Why DevOps (why did it come into existence)?
3. How do you introduce yourself for a DevOps role?
4. What are your day-to-day activities as a DevOps engineer?

!!! note "  STUDY TIP"
    In **real interviews**, these four questions are often asked back-to-back at the *very start* of the conversation. If you stumble here, **the interviewer may lose confidence** in you within the first five minutes. So this material is disproportionately high-value for the time it takes to learn.



## Why This Matters?

- These four questions are **not tool-specific**. You don't need to know Jenkins, Kubernetes, or Terraform to answer them.
- They test whether you understand the **purpose and mindset** of DevOps, not just the tooling.
- Getting these wrong early in an interview can end the conversation before your technical skills are even discussed.
- The Day 01 lesson is deliberately kept **simple and jargon-light**. Advanced concepts like *Containerization*, *Kubernetes*, and *Cloud-Services* are explicitly deferred to later episodes so beginners aren't overwhelmed.



## What is DevOps?

### The Problem With "Textbook" Definitions

The instructor notes that there are **hundreds of definitions** of DevOps depending on the source:
- AWS has its own definition.
- Red Hat has a different one.
- Every vendor tends to frame DevOps around its own tools.

Rather than memorizing one vendor's definition, we are going to build up a definition **from first principles**, layer by layer.

### Layer 01 - DevOps is a Culture, Not a Tool

!!! note "Core idea" 
    DevOps is a **culture / practice** an organization adopts to increase its ability to **deliver applications**.

- The **end goal of every organization** — Amazon, Flipkart, or a small startup — is to *deliver* something to the customer.
- Delivery speed is the single biggest business driver behind DevOps.

**One-line definition (v1):**
> "DevOps is a culture that improves an organization's ability to deliver applications."

### Layer 2 - Why Delivery Speed Matters (Examples from the video)

**Example 1 — Generic App (V1 → V2):**
If `example.com` takes **10 days** to move a new version of its application from V1 to V2 through Dev → Staging → Production, that is considered *slow* and a poor practice.

**Example 2 — PUBG bug/feature scenario:**
If there's a security issue or a new feature ready in PUBG, and it takes 10 days to ship it, that's a problem — because the fix should reach users almost immediately.

**Example 3 — Android security patch:**
If a vulnerability is discovered on Android that could let a hacker access a phone, Android needs to:
1. Build a fix.
2. Push a new version.
3. Get users to auto-upgrade.

Ideally this entire cycle happens in **hours**, or at most **1–2 days** — not weeks.

> 🎯 **Takeaway:** The faster and more reliably you can move code from a developer's machine to the customer, the more "DevOps mature" your organization is.

### Layer 3 - Is DevOps *Only* About Speed of Delivery?

A common misconception (explicitly called out in the video): people equate DevOps with **CI/CD** (Continuous Integration / Continuous Delivery) alone.

> **CI/CD** = Continuous Integration and Continuous Delivery — the practice of automatically building, testing, and deploying code changes frequently and reliably. *(Term mentioned in video; expanded here for clarity.)*

The instructor stresses: **delivery speed is necessary but not sufficient.** Speed without the following three things is dangerous.

### Layer 4 - The Manufacturing Analogy (Chips/Biscuits Factory)

To explain *why* speed alone isn't enough, the instructor steps away from software and uses a **factory analogy**:

> Imagine a company manufacturing chips (potato chips / biscuits). If it automates its factory so a full batch is produced in **one day** instead of many days — is that good enough?

- From the **manufacturer's side** → Automation ✅ (fast production)
- From the **customer's side** → Speed alone doesn't matter if the product is bad. Customers care about **Quality**.
- To make sure quality stays consistent, the factory needs **Monitoring** — someone/something has to flag it immediately if quality or the automated process breaks down.
- And to catch problems *before* they reach the customer, the factory needs **Testing**.

This analogy maps directly onto software delivery.

### The Four Pillars of DevOps

```
                        ┌────────────────────────────┐
                        │           DEVOPS            │
                        │  "Culture that improves     │
                        │   application delivery"     │
                        └──────────────┬───────────────┘
                                        │
            ┌───────────────┬──────────┼──────────┬───────────────┐
            │                │                     │               │
      ┌─────▼─────┐   ┌──────▼──────┐      ┌───────▼──────┐  ┌─────▼─────┐
      │ AUTOMATION │   │   QUALITY   │      │  MONITORING   │  │  TESTING  │
      │            │   │             │      │ (a.k.a.       │  │           │
      │ Remove     │   │ Ensure the  │      │ Observability)│  │ Continuous│
      │ manual     │   │ application │      │ Detect issues │  │ testing to│
      │ steps      │   │ meets       │      │ & report back │  │ catch bugs│
      │            │   │ standards   │      │ automatically │  │ early     │
      └────────────┘   └─────────────┘      └───────────────┘  └───────────┘
```

| Pillar | What it means | Why it matters |
|---|---|---|
| **Automation** | Removing manual/human steps from build, deploy, and infra processes | Speeds up delivery, removes human error |
| **Quality** | Application/code must meet a defined quality bar | Fast delivery of a broken product is worthless |
| **Monitoring** (a.k.a. **Observability**) | Continuously watching the system so issues are reported automatically | Lets teams react to failures before customers are badly affected |
| **Testing** | Continuous, ideally automated, testing throughout the pipeline | Underpins both quality and safe automation |

> 📝 **Note from the instructor:** Monitoring and Observability are described as "hand in hand" — closely related terms that will be explored together in a later, dedicated session.

### 2.7 Final Consolidated Definition (v2 — the one to memorize)

> **"DevOps is a process of improving application delivery by ensuring there is proper automation in place, by ensuring the application/code quality is maintained, by ensuring continuous monitoring, and by ensuring continuous testing."**

The instructor explicitly says this is the **ideal, complete definition** for Day 1 — good enough to give confidently in an interview.

### 2.8 What NOT to Say (Scope Control for Day 1)

The instructor deliberately **excludes** these advanced terms from today's definition — not because they're wrong, but because they'll be covered properly in later episodes:
- Cloud-native
- Serverless
- Shift-left

> 💡 **Interview tip:** It's fine to give a clean, simple, correct definition as a fresher. Over-stuffing your answer with buzzwords you can't explain is riskier than giving a solid basic answer.

### 2.9 Sample Interview Answer — "What is DevOps?"

> "DevOps is a process of improving the application delivery by ensuring there is proper automation, with application/code quality that is maintained, and by ensuring there is continuous monitoring and continuous testing in place."

### 2.10 The Business Outcome

Example given: if `example.com` currently ships a release every **2 weeks**, a DevOps engineer's job is to help bring that down toward **1 week** (or less) — *without* sacrificing automation, quality, monitoring, or testing.

## 3. Why DevOps? (The Historical / Before-and-After Story)

### 3.1 Setting the Scene

- **Developer** → writes the application code.
- **Customer** → the person who ultimately uses the application (web app, Android app, static site, etc.)
- The whole point of a company's existence is to get code from the developer safely and quickly into the customer's hands.

### 3.2 How It Worked ~10 Years Ago (Pre-DevOps Era)

Back then, there was **no single "DevOps engineer" role**. Instead, delivery required **three separate, siloed roles**, each doing one piece of manual work:

| Role | Responsibility |
|---|---|
| **System Administrator** | Provisions the server (and the application server) that will host the app. Before cloud platforms like AWS were common, this meant using **VMware**, **OpenStack**, or hypervisors like **Xen** on physical/bare-metal machines. |
| **Tester** | Tests the deployed application on the server the sysadmin created. |
| **Build & Release Engineer** | Takes the tested app and *promotes* it forward — first to a pre-production/staging environment, then (after re-testing) to production for the customer. |
| *(Developer, for context)* | Writes the code and checks it into a **centralized version control system** — e.g. **SVN** or **CVS** — so multiple developers can share code from one place. |

> ℹ️ **Terms explained:**
> - **SVN (Apache Subversion)** and **CVS (Concurrent Versions System)** — early centralized version control systems used before tools like Git became standard. Mentioned in the video as examples of where developers "checked in" code.
> - **VMware / OpenStack** — virtualization/cloud platforms used to provision servers before AWS-style public cloud became dominant.
> - **Xen** — a hypervisor used to create virtual servers on physical ("bare metal") hardware.
> - **Bare metal** — a physical, non-virtualized server. The video notes that "before 10 years, everything was bare metal."
> - **Application server** — the software layer on a server that actually hosts/runs the deployed application (distinct from the server/OS itself).

### 3.3 The Old Workflow, Visualized

```
 [Developer]
     │  writes code, commits to
     ▼
 [Central Repo: SVN / CVS]
     │
     ▼
 [System Administrator]
     │  provisions Server + Application Server
     ▼
 [App deployed on Server]
     │
     ▼
 [Tester]
     │  tests the app on that server
     ▼
 [Build & Release Engineer]
     │  promotes app forward
     ▼
 [Pre-Prod / Staging Environment]
     │  re-tested
     ▼
 [Build & Release Engineer]
     │  promotes again
     ▼
 [Production Server]  ────────────────►  [Customer]

     Total elapsed time for one release: ~10 days
     (example figure used by the instructor — could be more or less
      depending on the org, but the process was consistently slow)
```

### 3.4 Why Was It So Slow?

The instructor pinpoints the root cause plainly:

> **Multiple separate teams + manual, human-driven handoffs = slow delivery.**

- Every handoff between Developer → Sysadmin → Tester → Build/Release Engineer → Production required coordination, waiting, and manual work.
- There was no single owner responsible for the *entire* pipeline end-to-end.
- This inefficiency — not any single tool being "missing" — is what caused the **DevOps movement to emerge**.

### 3.5 What Changed With DevOps

- Instead of three-plus siloed teams, DevOps consolidates delivery responsibility into **one collaborative team/role**.
- Because there's no longer a rigid set of separate departments, DevOps *has* to be a **culture** — a shared way of working — rather than a fixed job description.
- Part of that culture is being willing to **adopt new tools** quickly. Example given: if your CTO identifies a new tool that improves efficiency, a DevOps engineer needs the mindset to adapt and pivot — this adaptability is itself a defining trait of the culture.

### 3.6 Old vs. New — Side-by-Side Comparison

| Aspect | Before DevOps (~10 years ago) | With DevOps |
|---|---|---|
| Teams involved | Sysadmin, Tester, Build & Release Engineer (separate) | One collaborative team/engineer |
| Process | Manual handoffs at every stage | Automated pipeline |
| Infra | Bare metal, VMware, OpenStack, Xen hypervisors | Often cloud platforms (e.g. AWS) |
| Release cycle | Days to weeks (e.g. ~10 days) | Hours to a couple of days |
| Mindset | Fixed role, fixed process | Cultural adaptability, continuous improvement |
| Core enablers | N/A (manual) | Automation, Quality, Monitoring, Testing |

### 3.7 Sample Interview Answer — "Why DevOps?"

> "Before DevOps, delivering an application required multiple separate teams — a system administrator to provision servers, a tester to validate the app, and a build & release engineer to promote it through environments. Because every handoff was manual and teams worked in silos, releases were slow — sometimes taking 10 days or more. DevOps emerged to solve this by bringing these responsibilities into a single collaborative culture built around automation, quality, monitoring, and testing — which dramatically speeds up and improves the reliability of delivery."

## 4. How to Introduce Yourself in a DevOps Interview

### 4.1 Common Mistakes (What the Instructor Has Seen Go Wrong)

- Candidates rush their self-introduction into **one or two minutes**, believing that's a hard rule. **It isn't.** Take the time you genuinely need.
- Candidates **omit their prior background**, which makes it harder for the interviewer to understand their fit.
- Candidates **exaggerate experience** — e.g., claiming 10 years of DevOps experience — which is not credible, since DevOps as a widely-known practice has really only been popular for the **last 7–8 years**.

> ⚠️ **Don't say:** "My organization adopted DevOps 10 years ago" or "I have 10 years of DevOps experience." These claims don't hold up and can lose the interviewer's trust immediately.

### 4.2 The Recommended Structure

A good self-introduction has **three parts**, in this order:

**Part 1 — Current DevOps experience**
State how many years you've worked specifically *as* a DevOps engineer (e.g., "4–5 years").

**Part 2 — Prior background (very important)**
Mention what you did *before* DevOps. Common prior roles mentioned in the video:
- System Administrator
- Build & Release Engineer
- Server Administrator
- Java Developer / Python Developer
- Automation Engineer

> 💡 **Why this matters (interviewer's perspective, as explained in the video):** If a candidate previously worked as a system administrator and the company uses AWS heavily, the interviewer can immediately see value: this person likely understands server administration and could help with automation or migrating on-prem infrastructure to the cloud. Your background gives the interviewer a mental model of where you'll add value.

**Part 3 — Roles & responsibilities, mapped to the Four Pillars**
Describe your day-to-day contributions using the same four pillars from Section 2:
- "I take care of **automation**..."
- "I ensure **quality** is maintained for the applications..."
- "I have set up **continuous monitoring**..."
- "I have automated **testing** into the DevOps lifecycle..."

**Optional Part 4 — Tools & Technologies**
The instructor says this is *optional* and not strongly recommended at the introduction stage, but if asked, you can mention things like:

| Category | Example Tool (as mentioned in video) |
|---|---|
| CI/CD | GitHub Actions |
| Container Orchestration | Kubernetes |
| Configuration Management | Ansible |
| Infrastructure Automation (IaC) | Terraform |

> The instructor deliberately keeps tool-talk minimal on Day 1 so beginners aren't overwhelmed — this will be expanded in later sessions.

### 4.3 What If You're a Fresher?

If you have no prior experience, keep it simple and honest:

> "I just started working as/learning to be a DevOps engineer. I'm passionate about learning DevOps..." — then optionally speak to what you've been learning.

You are **not** expected to invent a fake background.

### 4.4 Self-Introduction Template

```
1. WHO YOU ARE NOW
   "I am a DevOps Engineer with [X] years of experience in DevOps."

2. WHERE YOU CAME FROM
   "Prior to that, I worked as a [System Administrator /
    Build & Release Engineer / Server Administrator /
    Java Developer / Python Developer / Automation Engineer]."
   (Freshers: "I recently started learning DevOps and I'm passionate
    about it.")

3. WHAT YOU DO DAY-TO-DAY (map to the 4 pillars)
   "In my current role, I take care of:
      - Automation      → [what you automate]
      - Quality         → [how you ensure app/code quality]
      - Monitoring       → [how you monitor systems]
      - Testing         → [how testing is integrated]"

4. (OPTIONAL, if asked) TOOLS
   "I work with tools like GitHub Actions for CI/CD, Kubernetes for
    container orchestration, Ansible for configuration management,
    and Terraform for infrastructure automation."
```

### 4.5 Interview Do's and Don'ts Cheat Sheet

| ✅ Do | ❌ Don't |
|---|---|
| Take the time you need — there's no strict 1–2 minute rule | Rush your intro just because you think it must be short |
| Mention your real prior background (even non-DevOps roles) | Omit your background — it helps the interviewer place you |
| Be honest about years of experience | Inflate your years of DevOps experience |
| Map your responsibilities to Automation / Quality / Monitoring / Testing | Just list tool names with no context |
| Let freshers say they're new and passionate | Pretend to have experience you don't have |

## 7. Quick-Recap Cheat Sheet (For Fast Revision)

- **DevOps in one line:** A culture that improves an organization's ability to deliver applications, powered by **Automation + Quality + Monitoring + Testing**.
- **DevOps ≠ just CI/CD.** CI/CD is part of it, but quality, monitoring, and testing are equally core.
- **Why DevOps exists:** Before it, delivery needed 3 separate siloed roles (Sysadmin, Tester, Build & Release Engineer) with fully manual handoffs → releases took ~10 days. DevOps merges this into one collaborative culture to drastically cut that time.
- **Self-intro formula:** Current DevOps experience → Prior background → Responsibilities mapped to the 4 pillars → (optional) tools.
- **Golden rule for interviews:** Be honest about experience; your *prior* background (even non-DevOps) is valuable context for the interviewer, not something to hide.
- **Fourth interview question** ("day-to-day activities") was named but **not covered** in Day 1 — flagged here so you know to look for it in a later session rather than assuming it was answered.
